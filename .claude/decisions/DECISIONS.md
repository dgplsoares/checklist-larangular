# Decisões de Arquitetura (DECISIONS)

> Registro rastreável de decisões não triviais. Alimenta a seção de decisões do README.
> Formato: DEC-XXX — título · Contexto · Opções · Escolha · Trade-off.

## DEC-001 — Persistência: SQLite + Eloquent (não arquivo JSON)
- **Contexto:** o baseline persiste em `storage/tarefas.json` (race condition, sem lock, versionado no git).
- **Opções:** (a) manter arquivo com escrita atômica + lock; (b) banco relacional via Eloquent.
- **Escolha:** (b) SQLite + Eloquent — o `.env` já traz `DB_CONNECTION=sqlite`, então é `migrate` sem setup, e demonstra o idioma do framework.
- **Trade-off:** SQLite é suficiente para o teste; um SaaS real usaria MySQL/Postgres — mencionar no README como evolução.

## DEC-002 — Processo de desenvolvimento versionado em `.claude/`
- **Contexto:** o teste valoriza engenharia orientada a especificações (SDD) e uso de IA aplicada.
- **Escolha:** manter protocolo, plano, diário, decisões e o artefato preliminar de análise versionados em `.claude/`, tornando o método explícito e rastreável.
- **Trade-off:** adiciona docs de processo ao repositório; o ganho de transparência/rastreabilidade supera o custo.

## DEC-003 — Fluxo de refatoração: contract-first horizontal, testes woven, gate E2E único no fim
- **Contexto:** refactor de **uma** entidade com CRUD coeso — listar/criar/concluir/deletar compartilham o mesmo Model, migration, Controller, Resource, Service e a mesma árvore de componentes; os refatores maiores (componentização, signals/OnPush, error handling) são transversais. É preciso manter a app funcionando a cada fase (dev-protocol §6: "não big-bang") e o front consome um contrato de API que o backend define. Como sequenciar backend, frontend, testes e E2E?
- **Opções:**
  - **(A) Contract-first horizontal** — backend inteiro + feature tests → frontend inteiro + specs → E2E conectado no fim. *Prós:* fixa o contrato (shape do `TarefaResource`, 201/204/422/404, prefixo `/api`, `PUT|PATCH`) **testado antes** de o front consumir; segue a direção natural de dependência (front→back); as feature tests são o safety net de maior ROI e provam que a troca JSON→SQLite não regrediu; casa quase 1:1 com a estrutura existente. *Contra:* entre o fim da Fase 1 e o da Fase 2 a integração no navegador fica vermelha (o front antigo aponta para `/tarefas` e quebra no prefixo `/api`); o E2E real só roda no fim.
  - **(B) Vertical-slice por feature** — back+front de cada operação juntos, E2E por fatia. *Prós:* risco de integração aparece cedo e contínuo; "funcionando" satisfeito pelo navegador a cada fatia. *Contra:* numa entidade só, as operações **não** são verticais independentes — obrigam a levantar todo o scaffolding do back na 1ª fatia e reabrir os mesmos arquivos a cada fatia seguinte, com muito troca-troca PHP↔TS e quase zero isolamento; fragmenta os refatores transversais e a suite de testes; multiplica cerimonial de E2E sobre superfície pequena (gold-plating de processo).
  - **(C) Big-bang** — tudo de uma vez, teste só no fim. *Contra:* viola o §6 ("não big-bang"); remove a rede de segurança durante a mudança mais arriscada (JSON→SQLite, `/api`, CORS); com 16 achados mudando juntos, atribuir uma falha à causa fica difícil. Praticamente um não-partida dadas as restrições.
- **Escolha:** **(A) contract-first horizontal, com os testes tecidos por camada** — feature tests PHPUnit dentro da Fase 1 (backend) e specs Angular (TodoService via `HttpTestingController` + 1 spec de componente) dentro da Fase 2 (frontend) — reservando **um único gate de integração E2E manual/scriptado no fim** (Fase 5). Isso **dissolve a antiga "Fase 3 — Testes" separada** e a distribui nas fases de código (dev-protocol §2: testes adicionados junto com a refatoração, não depois). As feature tests **são o contrato executável**: pinam o shape do `TarefaResource` e os status antes de o front tocar neles, dando ao front um alvo estável e tipado (`interface Todo` espelhando o Resource). Sem framework de E2E automatizado (Cypress/Playwright) para uma entidade só — o "E2E" é smoke manual/scriptado, right-sized.
- **Trade-off:** entre o fim da Fase 1 e o da Fase 2, o app **integrado no navegador** fica vermelho (front ainda em `/tarefas`; o handler de erro do baseline mascara isso fabricando dados offline — mais um motivo para removê-lo na Fase 2). Aceito num refactor solo: "funcionando" é provado **por camada** (feature tests + curl no back; specs no front) e a integração é **re-provada no gate E2E final**, com o contrato pinado por testes nos dois lados. Bugs de integração puramente cross-layer (preflight/CORS na origem restrita, responsivo) aparecem mais tarde — mitigado pelo contrato tipado e testado em ambos os lados.
